# Правила работы

## Согласование реализации

- Перед реализацией или изменением кода предложить варианты решения, обычно 2–3. Для каждого кратко описать подход и основные плюсы и ограничения.
- Явно отметить рекомендуемый вариант и объяснить причину рекомендации.
- Дождаться, пока пользователь выберет или подтвердит вариант либо предложит собственное решение. До этого не менять код и не начинать реализацию.
- До согласования разрешены чтение кода, исследование и проверки, не изменяющие проект, необходимые для подготовки вариантов.
- После согласования выполнять выбранный вариант в согласованном объёме. Существенное изменение подхода или объёма сначала согласовать отдельно.
- Если пользователь просит подождать или пересмотреть подход, остановить реализацию. Не удалять и не откатывать уже внесённые изменения без согласования.

## Архитектура

- Согласованные архитектурные решения и границы ответственности описаны в [ARCHITECTURE.md](ARCHITECTURE.md). Читать перед изменением структуры проекта, моделей проектов/песочниц и жизненного цикла задач.
- Документ описывает целевую архитектуру; отличия текущего кода не означают разрешения на несогласованный рефакторинг. Существенное изменение границ сначала согласовать и затем отразить в документе.
- Перенос модулей отделять от изменений поведения и схемы данных. Сохранять существующие данные и проверять миграции.

## Коммиты и push

- В процессе согласованной работы можно и нужно самостоятельно делать промежуточные коммиты, когда это помогает сохранить осмысленную точку для отката. Отдельное подтверждение каждого коммита не требуется.
- Разбивать изменения на логически завершённые коммиты, чтобы к предыдущим рабочим версиям можно было корректно вернуться.
- Сообщение коммита должно содержать только title, без body.
- Не выполнять push самостоятельно. Push разрешён только по явной просьбе пользователя; обычно пользователь делает его сам.

## Git ignore policy

- Treat every repository's `.gitignore` as an intentional project policy.
- Never use `git add -f` or otherwise force-add a path ignored by `.gitignore` unless the user explicitly asks to add that exact ignored path.
- In particular, if a repository ignores `docs/`, do not add or commit files under `docs/`; keep generated plans and specifications untracked or place them only where the user explicitly requests.

## Слоёная карта кодовой базы

Когда просят разобрать кодовую базу, ветку или пайплайн на слои, показать структуру и контракты между модулями, найти мёртвый код или составить план зачистки — сначала прочитать `~/skills/layer-map/SKILL.md` и работать по этой инструкции.

Дополнительные материалы навыка: `references/method.md`, `references/authoring.md`, `references/install.md` и `assets/`.

Полосы упорядочены по зависимости, а не по номеру; каждое число на карте обязано иметь проверку в скрипте сверки; серая полоса «контракта нет» — это утверждение, а не недоделка.
