# Архитектура Sandbox Prepare

## Статус и область действия

Согласованное направление: модульный монолит в Cargo workspace, разделённый
на функциональные crates, с моделью состояния GPUI по принципам Zed.
Основные функции собираются в одно desktop-приложение. Watchdog остаётся
вспомогательным процессом для аварийной остановки окружений.

Этот документ описывает целевую архитектуру. Код уже разделён на функциональные
crates и поддерживает несколько проектов и песочниц, Git/Compose и восстановление
MySQL/Percona и ClickHouse. PostgreSQL остаётся в Roadmap.

Согласованное уточнение модели: одна рабочая директория проекта соответствует
одной песочнице. Создание и открытие рабочих копий находится в titlebar.
Новые дубликаты блокируются; старые конфликтующие записи сохраняются до явного
разрешения пользователем и доступны в меню существующих окружений.

Выбор архитектуры не означает переноса всех модулей или реализации всех
будущих функций за один проход. Раскладка существующих файлов по crates,
контракты и миграции оформляются отдельным согласуемым планом.

## Основные понятия

- **Проект (`ProjectId`)** — пользовательский проект: репозиторий, источники
  бекапов, конфигурация БД и варианты запуска приложения.
- **Песочница (`SandboxId`)** — выбранная рабочая директория проекта и
  управляемое приложением окружение вокруг неё: запуск, Compose-конфигурация,
  процессы, подключения и собственные данные БД. Одна рабочая директория
  соответствует одной песочнице; повторный выбор открывает существующую.
  У проекта могут одновременно работать несколько песочниц с разными
  рабочими директориями.
- **Поколение (`GenerationId`)** — конкретное восстановление БД песочницы.
  Recreate готовит новое поколение и переключает эту песочницу после
  успешных проверок; предыдущая рабочая версия сохраняется до переключения.
- **Набор бекапов (`BackupSetId`)** — проверенные архивы требуемых БД проекта.
  Состав зависит от проекта и не ограничивает модель обязательной парой.
- **Операция (`OperationId`)** — загрузка, проверка, восстановление, запуск
  или другое длительное действие с собственным состоянием и отменой.
- **Владелец установки и сессия приложения** — идентичности для определения
  принадлежащих приложению ресурсов и аварийной остановки.

Имя Docker Compose project — имя группы ресурсов запуска, а не идентификатор
пользовательского проекта. Поколение ресурсов и выбор исходного кода также
являются разными понятиями.

Git worktree определяет рабочие файлы, а `SandboxId` связывает их с настройками
и ресурсами окружения. Название ветки не является идентификатором песочницы:
ветка в рабочей директории может измениться, а её БД и конфигурация сохраняются.
Отдельное обязательное имя при создании не требуется; отображаемая подпись
берётся из ветки или имени каталога. Служебный каталог приложения с SQLite,
логами и конфигурацией Docker не является рабочей директорией исходников.

## Границы модулей и зависимости

Packages размещаются в `crates/<name>/`, внутренние модули — в каталогах
соответствующей функции. Crate выделяется по самостоятельной ответственности
и публичному API; каждый исходный файл не становится отдельным crate.

| Область | Ответственность |
| --- | --- |
| Запуск приложения | Сборка зависимостей, общий координатор, реестр задач, завершение работы, watchdog |
| Рабочее пространство | Окна, навигация, выбор проекта и песочницы, соединение экранов с сервисами |
| Проекты | Репозитории, варианты исходного кода, конфигурация источников и запуска |
| Бекапы | S3, выбор свежих объектов, локальный кеш, проверка целостности, публикация набора |
| Песочницы | Состояние окружений, поколения ресурсов, операции, подготовка и восстановление БД |
| Настройки | Модели предпочтений, валидация, сохранение и применение изменений |
| Наблюдение | Логи приложения и процессов, файловое хранение, ротация, будущие сборщики метрик и HTTP-событий |
| Общий UI | Компоненты GPUI, оформление, иконки, общие приёмы взаимодействия |
| Интеграции | Вызовы Git и Docker, файловые операции и доступ к SQLite за определёнными API |

Это границы ответственности; точный набор crates и размещение адаптеров
уточняются в плане миграции. Специфичный для функции адаптер может оставаться
внутри неё, общая интеграция выделяется при использовании несколькими модулями.

Правила зависимостей:

- Сборка приложения связывает функциональные модули и интеграции.
- Рабочее пространство и экраны используют публичные API функций. Изменение
  настроек соединения не должно требовать вызова одного экрана через другой.
- Функциональный модуль не зависит от конкретного окна или рабочего пространства.
- Общие UI-компоненты не зависят от функциональных модулей приложения.
- Общие интеграции не зависят от экранов и координатора приложения.
- Восстановление использует публичный API бекапов; бекапы не зависят от
  реализации песочниц. Политика файлового логирования не зависит от экрана настроек.
- SQL и детали внешних SDK остаются у репозиториев и адаптеров; они не
  становятся обязанностью обработчиков UI.
- Интерфейсы вводятся для значимых границ и подмены внешних систем в тестах.
  Отдельный trait для каждой функции не требуется.

GPUI допустим в моделях состояния, а не только в отрисовке. `Entity<T>`
не означает, что объект является экраном. Рабочие модели и задачи имеют
срок жизни приложения или песочницы; их существование не определяется
выбранной вкладкой. Блокирующая работа не выполняется в UI-потоке.

## Управление несколькими песочницами

Общий координатор хранит реестр контроллеров по `SandboxId`. Каждый контроллер
владеет состоянием своей песочницы, её операциями и подписками на процессы.
Независимые песочницы работают параллельно. Взаимоисключающие изменения
одного окружения применяются последовательно; длительная операция должна
оставаться доступной для отмены и остановки.

Каждая песочница имеет собственные контейнеры, тома БД, сеть, порты и
учётные данные. Общие лимиты тяжёлых операций учитывают ресурсы ПК и не
превращаются в глобальный запрет любой работы остальных окружений.

Начальная сверка ресурсов после запуска принадлежит координатору приложения.
Обычная операция одной песочницы не останавливает другие окружения установки.
Операции над ресурсами проверяют их владельца, песочницу и поколение.

UI получает снимки состояния и типизированные события с идентификаторами
проекта, песочницы и операции. Поздний результат предыдущей операции не
перезаписывает новое состояние. Частые значения прогресса и метрик можно
объединять; очереди и память для потоков наблюдения должны быть ограничены.

## Репозитории и выбор исходного кода

Поддерживается существующий локальный Git-репозиторий, в том числе без
настроенного remote. Удалённый URL является способом получить локальный
репозиторий через явную операцию клонирования. Для запуска используется
локальная рабочая директория; автоматический fetch или переключение ветки
при открытии приложения не предполагается.

Для песочницы пользователь выбирает один из режимов:

| Режим | Поведение | Владение каталогом |
| --- | --- | --- |
| Автоматический изолированный worktree | Приложение создаёт отдельную рабочую директорию на основе выбранной ревизии/ветки по правилам Git | Приложение учитывает созданный им worktree |
| Текущий checkout | Используется рабочая директория основного checkout проекта и фактически выбранная в ней ветка | Пользователь |
| Существующий worktree | Выбирается уже зарегистрированная рабочая директория этого репозитория | Пользователь |

Существующие worktrees обнаруживаются средствами Git, а не поиском только
каталога `.git`: у linked worktree `.git` может быть файлом. Сохраняются режим,
путь рабочей директории и сведения о владении. Приложение не предполагает,
что у репозитория обязательно существует `origin`.

В режимах текущего checkout и существующего worktree песочница использует
содержимое выбранной директории, включая доступные локальные изменения.
Это не создание второй копии кода: приложение привязывает управляемое окружение
к существующей рабочей директории. Выбор любой из трёх разновидностей источника
открывает уже связанную песочницу либо создаёт одну новую привязку.

Идентичность определяется реальной рабочей директорией, а не текстом пути,
именем ветки или названием окружения. Разные пути через символические ссылки
не должны создавать дубликаты. Проверка и создание привязки должны исключать
дубликаты и при одновременных запросах.

Переход сохраняет идентификаторы, конфигурацию, секреты, поколения БД и пути
уже созданных окружений. Старые записи без исходников или несколько записей
с одной директорией не объединяются и не удаляются автоматически: их требуется
явно связать или разрешить конфликт. Пока конфликт не разрешён, нельзя создавать
ещё одно окружение для той же директории. Отсутствующий каталог не является
основанием удалять запись песочницы или её данные.

Автоматический worktree создаётся из Git-ревизии; незакоммиченные,
неотслеживаемые и игнорируемые файлы не копируются в него автоматически.
Выбор ветки учитывает занятость в другом worktree; принудительный checkout
не используется для обхода конфликта. Пользователь выбирает свободную ветку
либо вводит имя новой ветки, создаваемой от текущей ревизии выбранной рабочей
копии. Автоматическое создание ветки с выдуманным именем и detached checkout
не используются. Основной checkout при этом не переключается.

Закрытие приложения останавливает контейнеры, но сохраняет рабочие директории.
Исходный checkout и выбранный существующий worktree приложение не удаляет.
Удаление собственного worktree — отдельная часть удаления песочницы;
наличие изменений требует сохранения работы пользователя, а не принудительной
очистки. Владение определяется записью о создании, а не одним расположением пути.

Выбор проекта и рабочей копии находится в titlebar. Рабочая копия уже определяет
песочницу, поэтому отдельный независимый селектор sandbox не требуется.
Меню рабочей копии предлагает изолированный worktree, текущий checkout и
существующий worktree; выбор ветки и существующего worktree выполняется в этом
же сценарии, без перехода на форму создания во вкладке Projects.
Git-снимки загружаются отменяемыми операциями вне UI-потока. Обычное переключение
контекста не выполняет checkout и не меняет исходники работающей песочницы.

Создание или открытие песочницы подготавливает рабочую директорию и сохраняет
привязку окружения. Оно само по себе не скачивает бекапы, не восстанавливает БД
и не запускает контейнеры. Настройка Compose и подключений принадлежит выбранной
песочнице; подготовка данных и запуск остаются явными действиями. Выход из
приложения останавливает все запущенные им окружения, сохраняя их рабочие копии,
настройки и данные для следующего запуска.

## Запуск Compose проекта

После выбора рабочей директории приложение ищет `.yml` и `.yaml` и предлагает
Compose-конфигурации. Произвольный YAML не считается конфигурацией Compose
по одному расширению. Обнаружение файлов не запускает контейнеры.

Модель запуска допускает основной файл, упорядоченные override-файлы,
выбранные profiles и сервисы. Относительные пути и build contexts должны
разрешаться относительно корректной директории конфигурации в выбранном
checkout/worktree. Перед запуском проверяется итоговая конфигурация.

Redis, RabbitMQ, Elasticsearch и другие вспомогательные сервисы описывает
сам проект. Sandbox Prepare запускает выбранное окружение и контролирует
жизненный цикл всех запущенных через него сервисов, включая вспомогательные.

Итоговый план связывает приложение с восстановленными БД этой песочницы.
Стандартные `DB_*`, `CLICKHOUSE_*` и `CLICKHOUSE_URL` подставляются в окружение
сервисов-потребителей; имена БД хранятся в профиле и проверяются после восстановления.
Расширенные ручные bindings остаются для нестандартных переменных. Исходные файлы
проекта не переписываются; env импортируется в SQLite, служебный Compose не содержит
секретных значений — они передаются процессу через окружение.

Переносимый профиль запуска принадлежит проекту и хранится в `project_launch_profiles`
(схема SQLite v4). Новая рабочая копия получает его копию; существующие песочницы
сохраняют свои настройки. Сохранение профиля и настроек выбранной песочницы атомарно.
Относительные mount paths разрешаются относительно выбранной рабочей копии.

`runtime::launch` координирует одну операцию Manager: проверку профиля, подготовку
актуальной пары бекапов при отсутствии данных, восстановление и запуск приложения.
Менеджер сохраняет единый busy/cancel/shutdown-контракт. Проверка S3 и загрузка общих
бекапов координируются сервисом проекта; ожидающая песочница не отменяет чужую загрузку.
Повторный Start сохраняет данные; только подтверждённый Update databases заменяет их.
Потеря одного volume требует явного обновления, отсутствующие контейнеры пересоздаются.
Docker назначает localhost-порты новым поколениям БД, Manager сохраняет реальные порты.

Готовность приложения проверяется по Compose healthcheck или явно настроенному
HTTP endpoint через опубликованный localhost-порт. Без проверки показывается Running
без подтверждённой готовности. Статус отражает проверку запуска, непрерывные метрики
БД и перехват внешнего трафика остаются отдельными будущими подсистемами.

Уникальное имя Compose project является частью изоляции. Планировщик также
учитывает фиксированные `container_name`, опубликованные порты, явные имена
томов, external-ресурсы, общие bind mounts и настройки перезапуска. Исходники
могут быть общими в выбранном пользователем режиме, но данные сервисов разных
песочниц не должны случайно становиться общими. Конфликт при фактическом
выделении порта обрабатывается даже после успешной предварительной проверки.

## Базы данных и бекапы

Проект задаёт требуемые управляемые БД. Текущие реализации — MySQL/Percona
и ClickHouse; архитектура предусматривает PostgreSQL. Восстановление и
проверки каждого движка имеют собственную реализацию. Версия PostgreSQL,
формат его бекапа и способ восстановления уточняются отдельно до реализации.

Тип движка, назначение БД, версия и формат архива задаются явно. Позиции
в массивах не должны быть единственным контрактом между модулями.

Один актуальный набор архивов хранится на проект в служебной директории.
Несколько песочниц могут использовать его без отдельных копий архивов;
восстановленные тома БД принадлежат каждой песочнице отдельно.

Новые архивы сначала скачиваются и проверяются, затем набор публикуется
атомарно. Предыдущие архивы удаляются после успешной замены, когда они
не используются восстановлением. Согласование чтения и замены набора
не должно запрещать совместное чтение неизменяемых файлов или блокировать
другие проекты. Конкретный механизм блокировок выбирается в плане реализации.

Быстрая проверка локальных файлов при старте сохраняется. Полная проверка
целостности выполняется при загрузке и по явному запросу. Обновление
бекапов не пересоздаёт уже работающие песочницы автоматически.

## Хранение и наблюдение

Метаданные проектов, песочниц, поколений и секреты хранятся локально в SQLite
с версионируемыми миграциями. Переменные окружения и `.env` не используются
как хранилище секретов Sandbox Prepare. Настройки интерфейса сохраняют
редактирование через JSON. Архивы, служебные файлы и логи остаются в
директории данных приложения с разделением по проекту и песочнице.

Логи приложения и процессов — разные источники. Текущий поток ограничен
настраиваемым числом записей, история хранится в JSON Lines с ротацией.
Записи получают контекст проекта, песочницы и операции; секреты маскируются.
SQLite не превращается в хранилище потоковых логов.

Метрики БД и мониторинг HTTP — будущие отдельные сборщики и представления.
Они не должны встраиваться в обработчики отрисовки или смешиваться с
управлением восстановлением. Выбор прокси, работа с TLS и хранение тел
запросов обсуждаются отдельно.

## Завершение и аварийное восстановление

При штатном выходе координатор:

1. Прекращает принимать новые операции.
2. Отменяет незавершённые операции и дожидается выхода их работников,
   включая блокирующие задачи и дочерние процессы.
3. Останавливает тестируемые приложения, вспомогательные сервисы и БД
   всех запущенных через Sandbox Prepare окружений.
4. Проверяет остановку, завершает сбор логов и сохраняет журналы.
5. Завершает работу приложения и вспомогательного watchdog.

Отмена — сигнал, а не подтверждение завершения. Очистка временных ресурсов
начинается после остановки использующих их работников. Данные песочниц
и рабочие директории сохраняются при обычном выходе.

При ошибке остановки приложение показывает ошибку вместо успешного выхода
с неподтверждённой очисткой. Watchdog дополнительно пытается остановить
ресурсы сессии после аварийного завершения; результат зависит от доступности
Docker. Следующий запуск сверяет сохранённое состояние с реальными ресурсами
и обрабатывает незавершённые поколения без удаления чужих данных.

## Переход от текущей реализации

Перенос файлов отделяется от изменения поведения и схемы данных. Миграция
должна сохранить существующие бекапы, песочницу, настройки и секреты в проекте
по умолчанию. Откат Git-коммита сам по себе не откатывает SQLite-схему.

При реализации проверяются публичные границы модулей, независимость
параллельных песочниц, адресная отмена, владение Git/Docker-ресурсами,
сохранность предыдущего рабочего поколения, выход приложения и восстановление
после аварии. Нужные проверки зависимостей и сценарии тестирования входят
в соответствующие этапы плана миграции.
