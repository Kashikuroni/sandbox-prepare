Локальное приложение для подготовки тестовых песочниц из бекапов БД и Git-проектов.

[ARCHITECTURE.md](ARCHITECTURE.md) фиксирует границы модулей и контракты,
[IMPLEMENTATION.md](IMPLEMENTATION.md) — выполненные этапы и проверки.
Приложение организовано в Cargo workspace; `cargo run` запускает desktop-приложение.

## Проекты и песочницы

Слева выбираются проект и песочница. У проекта свои S3-настройки, префиксы
бекапов и один актуальный набор архивов. У каждой песочницы — отдельные пароли,
тома БД, сети, порты и состояние. Можно одновременно запустить несколько
песочниц одного проекта и разных проектов. Переключение страницы не отменяет
загрузку или восстановление.

В **Projects → Project** добавляется локальный Git-каталог или явно выбирается
клонирование URL. Remote не обязателен; автоматического fetch нет. Новые проекты
получают исходную S3-конфигурацию выбранного проекта; затем её можно изменить
через **Settings → Storage**, а префиксы — через **Backup locations**.

В **New sandbox** доступны три режима:

- **New isolated worktree** — существующая свободная ветка или новая ветка от
  HEAD основного checkout. Незакоммиченные файлы основного checkout не копируются.
- **Current checkout** — текущий основной checkout без переключения ветки.
- **Existing worktree** — одна из уже зарегистрированных рабочих директорий.

Занятую ветку приложение не переключает принудительно: нужно выбрать её checkout
или worktree. **Remove sandbox…** удаляет данные после подтверждения; пользовательские
директории и ветки сохраняются. Собственный worktree удаляется только чистым и
незаблокированным. Иначе песочница остаётся в каталоге с сообщением об ошибке.

В **Launch** обнаруживаются Compose-файлы. Порядок выбора задаёт порядок их
объединения. **Inspect selection** показывает profiles, services и bind mounts.
Указанные сервисы БД заменяются управляемыми определениями с сохранением логических
имён и зависимостей. Redis, RabbitMQ и другие вспомогательные сервисы берутся
из Compose проекта и останавливаются вместе с песочницей.

Переменные из env-файла импортируются в SQLite для всех сервисов или выбранного
сервиса. Новые `.env` не создаются; исходные YAML и env-файлы не изменяются.
**Database bindings** задают переменную сервиса и значение из подключения к MySQL
или ClickHouse. Для bind mounts выбирается исходный код, read-only конфигурация
или отдельные данные песочницы; путь к коду/конфигурации можно заменить.
Внешние сети/тома требуют явного выбора частной замены; host networking,
external_links и тома с внешним драйвером/driver_opts не запускаются автоматически.
Опубликованные порты приложения назначаются Docker на localhost; фактические
порты сервисов можно посмотреть через Docker. Порты БД показаны в Sandboxes.

**Save launch configuration** сохраняет конфигурацию следующего создания или
пересоздания; работающие контейнеры сразу не меняются. Черновики Launch сохраняются
в памяти отдельно для каждой песочницы при переключении контекста. Для запуска
нужно скачать бекапы и выбрать **Sandboxes → Create from backups**.

## Настройки

Шестерёнка Zed справа в titlebar или `Cmd+,` (`Ctrl+,`) открывает отдельное
окно настроек. Повторное нажатие поднимает уже открытое окно. Слева поиск по
названиям и описаниям, а также разделы Appearance, Storage, Logging и Sandboxes.
Storage относится к выбранному проекту. В Sandboxes число параллельных тяжёлых
восстановлений по умолчанию равно двум и меняется с debounce-сохранением.
Поля Logging сохраняются автоматически после 300 мс без ввода; некорректные
значения не применяются и отмечаются ошибкой. Фокус и курсор при сохранении
остаются на месте.

**Edit settings.json** открывает многострочный редактор внутри этого же окна.
**Save JSON** проверяет значения и применяет их к формам и приложению. Перед
закрытием окна или переключением режима несохранённые изменения можно отменить
либо оставить для дальнейшего редактирования. Общие настройки хранятся в
`settings.json`; существующий `settings.toml` автоматически переносится при
первом запуске и сохраняется как исходная копия. Ключи S3 остаются в SQLite и
редактируются в Storage.

## Управляемые бекапы

На проект хранится одна текущая пара — ClickHouse и MySQL — в служебном
каталоге `projects/<project-id>/backups` рядом с `application.sqlite3` и `logs`.
Корень данных на macOS — `~/Library/Application Support/sandbox-prepare/`.
Импортированный проект сохраняет прежний путь `backups/`: миграция не переносит
файлы, не меняет старые Docker-ресурсы и сохраняет секреты. Перед изменением
существующей схемы SQLite создаётся копия в `migrations/`; откат Git сам по себе
не откатывает схему данных.

При запуске и по **Refresh** приложение проверяет наличие, размер и время
изменения локальных файлов, не читая их содержимое. Параллельно проверяются
последние объекты S3: endpoint, bucket, ключ, время изменения, размер и ETag.
ETag не трактуется как MD5. Изменённый локальный файл помечается как требующий
полной проверки или повторной загрузки.

**Verify integrity** отдельно проверяет оба локальных архива и сравнивает SHA-256
с сохранённым значением; работает и без доступа к S3. Повреждённые файлы остаются
на месте, результат ошибки сохраняется между запусками. Успешная проверка
обновляет локальное время изменения в манифесте. При отмене результаты предыдущей
проверки сохраняются. Быстрая проверка не обнаружит повреждение, если размер и
время изменения файла остались прежними — для этого нужна **Verify integrity**.
Старые манифесты получают базовое время изменения при первой быстрой проверке,
без повторного чтения архивов; исходный SHA-256 сохраняется.

Одна кнопка **Download** скачивает оба файла, если локальной пары нет или
она не прошла проверку. **Update** повторно скачивает оба файла при изменении
хотя бы одного объекта. **Up to date** означает, что оба объекта совпадают с
проверенными локальными копиями. При недоступности S3 локальная пара сохраняется,
а актуальность помечается как неизвестная.

Оба новых файла параллельно скачиваются в `.pending-*`. Завершившаяся загрузка
сразу поступает на проверку, пока второй файл продолжает скачиваться. Архивы
проверяются по одному, чтобы ограничить нагрузку на процессор и диск: размер
ответа и файла, полное чтение zstd, структура и заголовки TAR с метаданными
ClickHouse, контрольные суммы и полнота файлов xbstream для MySQL. Архивы не
распаковываются на диск; проверка не заменяет пробное восстановление БД.
SHA-256 считается в том же проходе чтения сжатого файла, что и проверка
архива, и сохраняется в манифесте. Сигнал **Cancel** или ошибка одного файла
останавливает загрузку и проверку обоих. Незавершённая новая пара удаляется
после остановки всех задач; предыдущая пара остаётся доступной.

После успешной проверки обоих файлов новый каталог переименовывается в `pair-*`,
синхронизируется на диск, а одна запись SQLite атомарно переключает текущую пару.
Только после этого удаляется предыдущий набор. Восстановления совместно читают
архивы; обновление может скачивать новые файлы, но публикация и удаление ожидают
завершения всех читателей. Ожидание можно отменить. При ошибке удаления показывается
предупреждение, очистка повторяется при следующем запуске/Refresh. Незавершённые
и неактивные наборы убираются под блокировкой каталога, защищающей от параллельной
работы нескольких экземпляров приложения. Во время обновления нужно место под
обе пары.

Диалогов сохранения и настройки папки больше нет. Старый `download_directory`
автоматически удаляется из JSON при загрузке без сброса остальных настроек.
Ранее скачанные пользователем файлы за пределами служебного каталога сохраняются.
Прогресс обновляется раз в секунду, показатели имеют фиксированную ширину и
табличные цифры. Завершение/отмена отображаются сразу, проверка архивов — отдельным
состоянием с процентом и объёмом прочитанных сжатых данных. Во время
верификации процент ограничен 99% до завершения структурных проверок.

## Базы данных в Docker

**Sandboxes** создаёт выбранную песочницу: Percona Server **8.4.11-11** и ClickHouse
**26.8.19.9**, с отдельным именованным volume для каждого сервера. Образы серверов
и XtraBackup 8.4 закреплены по digest; нужен запущенный Docker Engine с Compose.
Служебные файлы лежат в `sandboxes` рядом с SQLite. Локальные учётные записи
генерируются приложением и сохраняются в SQLite. Пароли хранятся в SQLite. Для БД создаются
конфигурационные файлы с правами 0600 в каталоге 0700. Сгенерированный Compose
содержит ссылки на значения; значения проектных environment передаются команде
только во время запуска и сохраняются в SQLite вместе с планом поколения.

**Create from backups / Recreate** закрепляет текущую локальную пару архивов
под блокировкой. MySQL распаковывается потоком непосредственно в новый volume,
проверяются метаданные полного бекапа и версия сервера, затем выполняется
`xtrabackup --prepare` и выставляются реальные UID/GID пользователя mysql.
ClickHouse восстанавливается штатным `RESTORE` из read-only локального архива.
После восстановления архив отсоединяется от контейнера. Проверяются подключения,
число таблиц и чтение строк из выборки до 20 обычных таблиц каждой БД.
После БД запускаются выбранные проектные сервисы; при ошибке их запуска
предыдущий план приложения запускается повторно.
Исходные бекапы не изменяются; дополнительного полного прохода проверки перед
восстановлением нет. Свободное место проверяется внутри Docker, но точный объём
распакованных данных заранее неизвестен: ошибка заполнения диска сохраняет старую пару.

При пересоздании используются два новых volume. Рабочая пара сохраняется до
успешной проверки новой; SQLite переключает обе БД вместе, после чего удаляются
старые контейнеры и volume. На время операции требуется место под оба поколения.
Прерванное восстановление не продолжается поверх частичных файлов: Refresh
убирает собственное незавершённое поколение, после чего его можно запустить заново.

**Stop** сохраняет данные, **Start** поднимает существующие БД, **Delete** с
подтверждением удаляет оба volume и частные данные сервисов проекта, сохраняя
скачанные архивы и Git-источники. Recreate также
предупреждает об удалении локальных изменений после успешной замены.
Параметры подключения копируются из Sandboxes: с хоста через localhost,
из другого Compose-проекта — после подключения к указанной Docker-сети по
логическим именам сервисов из сохранённой конфигурации. Порты по умолчанию 13306, 18123 и 19000;
если они заняты, приложение выбирает свободные и показывает фактические значения.

При закрытии окна или Cmd/Ctrl+Q приложение отменяет текущую операцию, останавливает
контейнеры всех своих песочниц, включая приложения и вспомогательные сервисы,
и завершает команды чтения логов перед выходом. При ошибке
обычного закрытия окно остаётся открытым для повторной попытки. Отдельный
сторожевой процесс отслеживает закрытие канала владельца и при аварийном выходе
останавливает контейнеры только своей сессии. Автоперезапуск отключён.
Остановка через Docker API требует работоспособного Docker Engine; при следующем
запуске дополнительно согласуется состояние оставшихся собственных ресурсов.
Сторонние контейнеры и volume не обслуживаются.

**Processes** показывает вывод БД, сервисов проекта и восстановления выбранной
песочницы. Доступны поиск процесса в селекторе, пауза просмотра и виртуализированный
список. Память имеет один общий лимит для всех песочниц; записи содержат идентификаторы
проекта и песочницы. JSON Lines-файлы лежат в `sandboxes/<sandbox-id>/process-logs`
(у импортированной песочницы сохраняется `sandboxes/process-logs`). Ротация использует
Logging; пароли маскируются. Это отдельный источник от правой панели логов приложения.

## Сборка и проверки

```sh
cargo run --offline
cargo fmt --all --check
python3 scripts/check_architecture.py
cargo clippy --workspace --all-targets --offline -- -D warnings
cargo test --workspace --offline
cargo build --offline
```

Интеграции запускаются явно, используют одноразовые ресурсы и очищают их:

```sh
cargo test --workspace --offline compose_round_trip -- --ignored --nocapture
cargo test --workspace --offline docker_restores_both -- --ignored --nocapture
cargo test --workspace --offline two_sandboxes_share -- --ignored --nocapture
cargo test --workspace --offline global_shutdown_stops -- --ignored --nocapture
cargo test --workspace --offline watchdog_stops_only -- --ignored --nocapture
```

## Логи приложения

Кнопка с жуком Zed справа внизу открывает правую панель логов. Ширину можно
менять перетаскиванием её левой границы. Горячая клавиша: `Cmd+Shift+L`
на macOS или `Ctrl+Shift+L`.

- **Current** — живые логи текущего запуска из памяти, по умолчанию последние
  2000 записей. Лимит меняется в **Settings → Logging → Current log records**,
  применяется автоматически и сохраняется между запусками.
- **History** — отдельное постраничное чтение JSON Lines-файлов, включая
  предыдущие запуски. **Refresh** перечитывает историю. Источники не склеиваются.

В компактном списке показаны местное время в формате
`DD.MM.YYYY HH:MM:SS`, затем жирный цветной уровень и первая строка сообщения.
Кнопка **Details** справа
открывает полный лог с сообщением, категорией, сессией, номером и всеми полями.
**Back** возвращает к списку, а **Copy** справа вверху копирует полную запись
в JSON. Исходная UTC-метка времени сохраняется в файлах и JSON.
Под вкладками находятся два выпадающих фильтра: **All categories** и
**All levels**. Меню отрисовываются в GPUI, поддерживают стрелки, Enter и Escape;
выбранный пункт отмечается галочкой. Справа — иконка **Refresh** Zed.
Уменьшение лимита Current не удаляет записи из файлов. Граница ресайза не подсвечивается;
при наведении изменяется только курсор.

Логирование начинается до запуска окна. Файлы `.log` создаются в каталоге
`logs` рядом с `application.sqlite3`; на macOS это
`~/Library/Application Support/sandbox-prepare/logs/`. Запись выполняется
отдельным потоком. В Settings → Logging настраиваются:

- размер файла (по умолчанию 10 МиБ); порог проверяется перед каждой записью,
  целая запись может превысить его;
- срок хранения (7 дней с последней записи);
- интервал проверки срока хранения (24 часа);
- число полных записей в Current (2000).

Автоматическая проверка выполняется по расписанию, включая запуск приложения,
если наступил срок. Время и результат последней проверки сохраняются в
`logs/maintenance.json`, поэтому перезапуск не сбрасывает расписание.
**Check now** сначала применяет ожидающие корректные правки Logging, затем
запускает проверку и удаляет просроченные файлы. При ошибке в поле проверка
не запускается.
Текущий открытый файл исключён из удаления по возрасту. **Clear all logs…**
после подтверждения закрывает текущий файл, удаляет файлы логов, очищает Current
и начинает новую историю. Обе операции показывают число удалённых файлов,
освобождённое место и возможные ошибки. После удаления History перечитывается.
Обрабатываются только обычные файлы приложения с именем
`<session timestamp>-<pid>-<part>.log`; посторонние файлы и симлинки сохраняются.

Для безопасной проверки native UI debug-сборки поддерживают
`SANDBOX_PREPARE_TEST_DATA_DIR`: отдельный временный каталог настроек, базы
и логов. В release-сборке эта переменная не используется.

Для новых событий используйте `tracing` с категорией в target, например:
`tracing::info!(target: "app::s3", prefix = "ch/", "Looking for latest backup");`.
Ключи доступа регистрируются для маскирования до логирования операций;
поля с названиями secret, password, access_key, token, credential и authorization
скрываются до передачи записи в память и файловый поток.
